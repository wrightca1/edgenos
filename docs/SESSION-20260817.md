# 2026-08-17 — the replay is exonerated, and Et2 comes up without a reboot

An index of the session. Each finding links to the document holding its evidence.

## The shape of it

The session set out to name the write that tears Et2's link down. There isn't one. The hunt's
instrument worked exactly as designed and returned a clean negative, which killed the longest-running
open hypothesis on the checklist and replaced it with something more useful: Et2 can now be driven up
and down on demand, so a trial costs seconds instead of a reboot and a coin flip.

The method mattered more than the answer. **Disabling does not work in slices 15 and 16** — removing
the firing entry, or the whole slice, drops the frame, because those slices require a CAM match. Only
slice 14 shows the "edit moves and the frame survives" signature that found the `SKIP`. `0xe0` was
identified instead by **swapping the command byte with the Valid bit left set**, so the entry still
matches and only the operation changes.

## Fixed

- **`fm6000_lanelink` drove every port with Et1's TX polarity.** `patch_tx_cfg()` masked only the
  equalisation fields, so `TxPolarityInvEn[30]` passed through from the Et1-recorded template. It now
  comes from `FM6000_SERDES_PORTS[].txpol` — a field the table already carried and the tool ignored.

## Retracted, or refused

| claim | why it fell |
|---|---|
| "Some write between op 190,464 and 195,584 knocks Et2 down" | the window is a bulk L2L table fill, and the good boot ran the same writes with the link up. There is no write to find |
| "Et2's outcome is a race inside the replay" | the replay stops touching the port at op 157,123 and runs 63,849 more ops. Nothing races |
| "Correcting the TX polarity fixes Et2" | **not claimed.** 0/10 against a 2/10 baseline, Fisher p = 0.47. The bug is real and fixed on its own merits; the cure is unproven |
| "Coordinating a far-end bounce fixes it" | **not claimed.** 0/5, Fisher p = 0.52. At a 20% base rate 0/5 arises a third of the time — the test had no power |
| "`lanelink` brings Et2 up 2 times in 10" | **my own, same session.** The lane *oscillates*; a single delayed read samples the flap, it does not score an attempt. Every trial count in that section — including both comparisons above — measured a duty cycle it did not know it was measuring |
| "…so single-sample boot classification is unsound too" | **over-reach, corrected same session.** Fresh boots are unambiguous — 0/20 or 20/20 — because the flapping is an artifact of *driving* the lane. The historical 5-of-10 figure stands |
| "six boots all came up dark" | the box **never rebooted**. `reboot` returns 0 and does nothing here; `/proc/uptime` read 8 hours across all six "boots" |

## The method lessons, which transfer

- **A negative from a well-built instrument is a result.** `resolve-teardown.py` was written to name a
  culprit and instead proved there was none. That retired more open work than a positive would have.
- **Put the control in the same artifact.** Every conclusion here turned on reading the *good* boot
  over the same op range. The teardown window looked damning until the working boot was laid beside it.
- **Two independent sources beat a significance test.** The polarity map was settled by the EOS
  capture and the board's own FDL agreeing — no statistics needed. The *effect* of fixing it needed
  statistics, and did not survive them.
- **Fix what is provably wrong; claim only what is measured.** Bit 30 was wrong versus EOS and is now
  right. That is a separate sentence from whether it cures the link, and conflating the two is exactly
  how the splice became a published root cause.
- **Report power, not just p.** 0/5 and 0/10 read like refutations and are not. Recording
  P(0 successes | 20%) = 0.33 and 0.11 beside them stops a future reader citing them as evidence.
- **Establish that the signal is steady before counting it.** A whole afternoon of trial counts
  turned out to be single samples of an oscillating lane. No amount of statistical care on top of
  that fixes it — the defect was in the *measurement*, not the analysis. Sample a window with a
  simultaneous known-good control before any quantity gets a denominator.
- **Then check the correction, too.** Concluding "so all single-sample classification is unsound"
  was a second over-reach in the opposite direction, and one fresh-boot measurement refuted it.
  A correction is a claim and needs its own evidence.
- **Verify the action, not just its return code.** `reboot` exits 0 and does nothing on this box.
  Six data points were collected from a machine that had been up eight hours. Any harness step that
  is supposed to change the world must be confirmed *by observing the world* — `/proc/uptime` here.
- **A control that cannot fail is not a control.** The Et1 guard existed to prove the sweep was
  valid; the one time it read 0/20 it exposed a stale-log bug that would otherwise have been recorded
  as a dark boot. Put a quantity in every sweep whose correct value you already know.
- **The far end is not a mirror.** Our transmitter stays on while our receiver is dark, so the peer
  reports the link up either way. Asymmetry is the phenomenon, not an artifact.

## Where it stands

- **`tools/fm6000-status.sh`** reads live port state off the chip any time, no reboot, no log
  scraping. This removes the failure mode that cost two dark traces.
- The Et2 question is now sharp and *not* about stability: when it comes up it is a clean, stable
  link, indistinguishable from Et1 over five minutes. The question is **why autonomous training
  converges on some boots and not others**, given a byte-identical write stream that stops touching
  the port 63,849 ops before the end — and, separately, **why our `lanelink` DFE path reaches only a
  `HiBer` flapping lock** where the boot path reaches a clean one. The second is testable in seconds
  and is the better lead: it is a difference between two of *our* sequences, both of which we hold.
- `tools/et2-goodboot-measure.sh` does the reboot-until-good-then-measure cycle correctly, including
  all three reboot traps and the Et1 control. Roughly one good boot per two attempts, ~5 min each.
- **Open:** B1 (FFU ByteMux); bank 4's unchanged result against its MAC association; `DECREMENT` still
  unidentified; `mod_decode.py`'s reading of `0x05`/`0x85` still needs re-attributing.
- ⚠ `/mnt/flash/wdog.off` is still in place from the experiment runs and must be removed, or the
  auto-started watchdog disables itself.
