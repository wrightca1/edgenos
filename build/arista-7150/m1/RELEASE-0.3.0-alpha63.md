# 0.3.0-alpha63 — a second transcribed file retires: 58,364 → 52,702

alpha61 retired `fm6000_l2arpre` and closed with a note that `eplseq`, `mapperpre`
and `mgmt2pre` had not been checked for the same relationship. They have been now,
and they give three different answers. One of them retires here.

## The check

For each transcribed file, ask whether other generators already write every address
it writes, and where they disagree, ask a **register snapshot from a working boot**
which value is the one a working chip actually holds.

| file | addresses nothing else writes | disagreements | adjudicated |
|---|---|---|---|
| `eplseq` (22,051 writes / 1,027 addrs) | 0 | 0 | — identical final state to `eplinit` |
| `mapperpre` (5,662 / 712) | 0 | 124 | **124–0 against `mapperpre`** |
| `mgmt2pre` (1,541 / 510) | **8** | 0 | not retirable as-is |

## `mapperpre` retires

`fm6000_mapperinit` + `fm6000_mapper` already cover all 712 of its addresses. On the
124 where they disagree — mostly `MAPPER_SRC_PORT_TABLE`, plus the DMAC/SMAC CAMs —
the working-boot snapshot matches the other two on **all 124 and `mapperpre` on
none**. It was already redundant at runtime too: `mapper` runs later via `gen_list`
and overwrote it.

Measured with it disabled, then with it deleted:

| | alpha62 `PRESPLIT=0` | alpha63 (deleted) |
|---|---|---|
| sampled addresses matching a working boot | 1,125 / 1,125 | **1,125 / 1,125** |
| of which `mapperpre`'s own | 712 / 712 | **712 / 712** |
| routes in silicon | 14 | 14 |
| unicast to the switch | 0% loss | **0% loss** |
| unicast through the switch | 0% loss | **0% loss** |

⚠ Kernel route count read 44 on alpha62 and 38 on alpha63. Those two boots run the
**same** configuration as far as this change is concerned, so the count varies boot
to boot with what the peer advertises; it is not a regression. Forwarding is 0% loss
in both.

## `eplseq` stays, and the reason is interesting

`eplseq` and `eplinit` write **the same 1,027 addresses and reach exactly the same
final values** — zero disagreements. By the `mapperpre` test it looks retirable.

It is not, and the ratio says why: 22,051 writes over 1,027 addresses is **21.5
writes per address**. `eplinit` writes the converged state once. EPL is the port and
SerDes bring-up, so those repeats are link training — a protocol, not a value.
Identical end state is exactly what you would expect and proves nothing here.

This is the distinction the whole project turns on, and `eplseq` is the clean example
of it: **a file whose content is fully reproduced elsewhere can still be irreplaceable
for its sequence.** Retiring it needs the training conversation understood, not a
diff.

## `mgmt2pre` stays, for now

It writes 8 addresses `mgmt2init` does not, and all 8 are CRM — the counter-rate
monitor. On a working chip none of `mgmt2pre`'s values survive (it writes zeros;
the chip holds `03800000`, `97d00200`, `37b90d8f`), because the engine owns those
registers. That makes 7 of them inert.

The eighth is not obviously inert: `CRM_CTRL` gets `00000001` and reads back
`00000000`, which is the signature of a **self-clearing start strobe**. Dropping it
would silently stop whatever it starts. Retiring `mgmt2pre` means moving that strobe
into `mgmt2init`, not deleting it — small work, but work, and it is not done here.

## ⚠ The config hook did not work, and read as if it did

alpha61 added `/mnt/flash/fullseq.conf` so generator gates could change without a
rebuild. `PRESPLIT=0` was written to it, sourced cleanly, and **had no effect
whatsoever** — the boot still ran `mapperpre` and said so.

Sourcing a file sets plain shell variables. `init-m1` invokes the bring-up sequence
with an explicitly named environment, so anything not on that list never arrives.
alpha61 named three variables by hand, and `PRESPLIT` was not one of them.

Fixed with `set -a` around the source, so every assignment in the file is exported
and the hook is genuinely generic. The hand-written passthrough list is gone.

Worth stating plainly: the failure mode was a config file that is read successfully
and ignored silently. The only reason it was caught is that the boot log names each
generator as it runs, so "MAPPER pre-loop generated by us" appearing under
`PRESPLIT=0` was visible. A gate whose effect is not visible in the log would have
produced a confident, wrong result.
