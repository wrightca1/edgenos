# 0.3.0-alpha34 — L3AR slice 4 authored

Second L3AR slice replaced by a generator. Otherwise alpha33.

## What changed

`asic/fm6000/fm6000_l3arslice4.c` (generated by `asic/fm6000/tools/gen_l3ar_slice4.py`)
programs L3AR slice 4 — **QoS classification plus ALU46 operand selection**:

    rule N     an FFU classification condition          -> QoS profile
    rule N+1   the same condition AND a port qualifier  -> QoS profile + ALU46 operand

The qualifier is `SRC_PORT_ID4=0x00/0x20` with `FFU_DATA_W8A=0x80/0xd0`. A slice resolves last
match wins, so the qualified rule sits at the higher index and wins when the qualifier holds;
the unqualified rule below it overrides still-lower rules when it does not. The conditions are
the FFU's `FFU_DATA_W8B`/`W8C` nibbles plus two `ACTION_FLAGS` cases.

**625 writes, all 25 rules.** Unlike slice 1, none is redundant — dropping an unqualified rule
would let a lower-indexed rule match and select a different QoS profile.

`--verify` is a **byte comparison** here (we emit the same rule count as EOS, so byte equality
is the right test): **625 of 625 words identical**. Address sets are disjoint from
`fm6000_l3arinit` (slice 0, 640) and `fm6000_l3arslice1` (810) — checked, zero overlap.

## ⚠ A decoder bug this found

`l3ar_decode.py --actions` read only **word 0** of RAM4 and RAM5. Both are two words, and RAM4's
fields run to bit 54 — so the policer and QoS mux (`MuxOutput_QOS` at 49, `QOS_PROFILE` at
50-54) and the top bits of `ALU46_OP_PROFILE` (which spans 29-33) were invisible.

Consequences, both corrected: slice 4 was described as "ALU46 only" when it is really QoS
classification, and its rule 24 was reported as operand profile **3** when word 1 bit 0 makes it
**11**. Caught only because the generator byte-verifies against the image — the functional
decode looked entirely plausible. `--actions` now reads both words; slice 4 reports RAM4 25/25
nonzero rather than 13/25.
